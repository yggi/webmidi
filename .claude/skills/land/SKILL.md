# Land a pull request

Agents don't merge (`AGENTS.md`): this skill runs only on the owner's word, after a review that found nothing serious.
webmidi is a package, so nothing deploys: a merge reaches the frontends only through a tag, and the owner creates the tag (`AGENTS.md`: a release is a tag; cells' `release` skill is the model).
Do the steps in order and stop at the first that fails.

Lifted from yggi/cells .claude/skills/land/SKILL.md (yggi/cells#67), itself lifted from yggi/cell-studio's @ 85175ce without its deploy and live check; the issue handling (step 5) is the family's, 2026-10-16 (yggi/music-commons#4).

The REST API does all of it (`gh api`; a session's proxy refuses GraphQL, so `gh pr merge` and `gh issue close` may fail).
Every comment posted from a session ends with a blank line, `---` and `_Generated by [Claude Code](https://claude.ai/code)_`.

1. **The pull request is ready.**
   It is out of draft, and its *Verified* names its current head as the commit that passed the pre-push hook (`npm run verify`, and the count of tests the hook printed).
   It has no conflicts with `main` (`gh api repos/yggi/webmidi/pulls/<n> --jq .mergeable_state` is not `dirty`; otherwise `git merge origin/main` into it once, verified again), and CI on the head is green or blocked, never red.
   A change to what goes on the wire says so, with its line in `CHANGELOG.md`.
2. **The owner has approved.**
   In the prompt ("merge if you find nothing", and nothing was found), or as a yes to the review's summary.
   Otherwise stop and ask.
3. **Merge it by squash**, the pull request's title as the message, so `main` reads `Title (#n)`: `gh api -X PUT repos/yggi/webmidi/pulls/<n>/merge -f merge_method=squash -f commit_title="<title> (#<n>)"`.
   A merge commit only when a reader of `git log` needs the branch's steps, and the pull request says why.
4. **Update `main`.**
   `git fetch origin main && git checkout main && git merge --ff-only origin/main`, in a clone whose tree is clean.
5. **Handle its issues.**
   **A text the owner wrote is never edited**: the session appends its footer to every body or comment it writes, so an edit would sign the owner's words as Claude's. Where a step below would edit one (a tick in the owner's epic, a reference in the owner's issue), post a comment instead. Epics and issues Claude wrote (they end with the footer) may still be edited.
   1. **Closed as said:** every `Closes #n` in the merged pull request closed its issue (`gh api repos/yggi/webmidi/issues/<n> --jq .state`).
      One that didn't (a `Closes yggi/<repo>#n` in another repository, a typo) is closed by hand, with a comment naming the pull request: `gh api -X PATCH repos/yggi/<repo>/issues/<n> -f state=closed -f state_reason=completed`.
   2. **Ticked:** a `Part of #n` epic's checklist line for this pull request is ticked, `- [x] … (#<pr>)`, by rewriting the epic's body with that one line changed (`gh api -X PATCH repos/yggi/webmidi/issues/<n> -F body=@<file>`).
      An epic with no line for it gets one comment naming what landed.
      A frontend's pull request that moves onto webmidi ticks its line in this repository's epic the same way.
   3. **Follow-ups filed:** each line of the pull request's *Not done / follow-ups* that names work becomes an issue, or is one already and is linked, in the repository where it belongs: the wire's here, a language question in yggi/cells, a frontend's in yggi/cell-studio, yggi/jambot or yggi/KO-Multitool, one across the family in yggi/music-commons.
      The issue states its bounds as numbers (the `task` template).
   4. **References right:** an issue or pull request in another repository that the merged pull request mentions by a bare number is written `yggi/<repo>#n`, in its body and its comments; a bare `#n` here always means webmidi's own.
6. **No deploy.**
   A change a frontend would notice waits under *Unreleased* in `CHANGELOG.md` until the owner tags a release.
7. **Say so** in a comment on the pull request: the merge commit, the issues closed, the epic line ticked, and the follow-ups filed, each by its number.

If a step after the merge fails, the merge stands: fix forward on a new branch, and say on the pull request what is left.
